## 1. Lifecycle model

```text
version-controlled Seed
  draft + approved
        |
        | explicit import and publish
        v
formal runtime SQLite
  published
```

`published` is a SQLite lifecycle state. It must not be written into `knowledge_base_version.json`; the version-controlled Seed remains `draft` so it can be imported and explicitly published into a controlled runtime database.

## 5. Backup behavior

The publisher creates a timestamped external backup directory. When a live database exists, it uses SQLite Backup API rather than a raw open-file copy. When `.env` exists, it stores an exact private backup.

The secret-free manifest records:

- formal database and backup paths;
- whether a database and `.env` existed before release;
- pre- and post-release file Hashes;
- previous and target versions;
- approved Canonical Hash;
- candidate/effective verification result paths;
- rollback script and command paths.

The manifest and result must never include `.env` contents, API keys, tokens, passwords, private keys, full resumes, or full JDs.

## 6. Candidate publication

Candidate creation:

- existing live database: consistent SQLite Backup API clone;
- missing live database: compatible schema revision 1 initialization.

Target handling:

- absent: import and publish;
- identical draft: idempotent import and publish;
- identical published: accept;
- conflicting Hash, retired state, or incompatible schema: stop.

The candidate must expose:

2. recheck exclusive database access and sidecars;
3. use same-directory `os.replace()` to atomically replace the live database;
4. atomically write `.env` with target version;

6. repeat the full runtime acceptance against the live database;
7. launch the real Streamlit application headlessly;
8. require localhost `/_stcore/health` HTTP 200 and body `ok`;
9. terminate only the Streamlit process created by the publisher.

## 9. Failure handling

Before cutover, a failure leaves the live database and `.env` unchanged. The candidate and backup directory remain for diagnosis.

After cutover, a failure triggers compensation:

- restore the pre-release database backup or remove the newly created database;
- restore the previous `.env` content with an explicit `2026.07.1` assignment;
- verify effective version and database path;
- preserve the backup, result, and compensation evidence.

Never automatically retry or modify source code after a gate failure.

## 10. Guarded rollback

After successful publication, the backup directory contains `rollback.ps1`. Run it only after stopping the application:

```powershell
& "<backup-directory>\rollback.ps1"
```

Rollback refuses to proceed when the current database or `.env` Hash differs from the recorded post-release state. This prevents overwriting legitimate later changes.

A successful rollback:

- restores the pre-release database, or removes a database created by the release;
- writes an explicit effective version `2026.07.1`;
- preserves the approved Seed commit;
- performs no Git action.

Source-code rollback is a separate human decision; the runtime rollback script does not execute `git reset`, `git checkout`, `git revert`, or any remote operation.
