- Design date: 2026-08-05
- Target branch: `feature/knowledge-base-v1.1`
- Baseline HEAD: `265d299ed704ec29a76470a992a94751f193ec12`
- Software version: `1.1.0`
- Formal knowledge version: `2026.08.1`
- Current canonical hash: `0052ea7d63e09d8f0af49f62df8f876ac5bd2de0c8347262d67bd8e872261727`
- Current lifecycle: Seed version `draft`; 182 reviewable entities `pending`

## 1. Purpose

Phase 11.10C creates a separate, fail-closed Publisher decision layer after Author, role-level Reviewer, cross-role consistency review, release regression, and clean-environment acceptance have completed.

The Publisher layer answers five questions:

1. Is the version-controlled Seed internally complete and traceable?
2. Are the 21 sources suitable for the limited public-repository uses recorded in the review packages?
3. May all 182 reviewable entities transition from `pending` to `approved` without changing business content?
4. Can the approved Seed be imported and published in a temporary SQLite database using the current production lifecycle code?
5. Which later actions remain explicitly outside this phase?

Phase 11.10C does not create or edit the production runtime database, switch the default knowledge version, publish a Git tag, create a GitHub Release, create a PR, or push.

## 2. Critical lifecycle distinction

The version-controlled Seed and the SQLite runtime lifecycle deliberately use different status mechanisms:

- `knowledge_base_version.json` must remain `status: draft`; `KnowledgeVersionSeed` rejects `published` Seed input.
- Reviewable Seed entities transition from `review_status: pending` to `review_status: approved` only after the owner acts as Publisher.
- The Seed canonical hash changes when review statuses change because review status is part of canonical business content.
- Runtime publication occurs only after import, through `KnowledgeVersionPublisher.publish()`, which changes the SQLite version record from `draft` to `published`.
- The version-controlled Seed is never edited to `status: published`.

This distinction is a release invariant and must be explicit in all Publisher documents and tests.

## 3. Roles and separation of duties

### 3.1 Author and analytical reviewer

ChatGPT prepared the knowledge content, role-level review packages, cross-role consistency review, release-readiness analysis, and Publisher recommendation.

### 3.2 Owner / Publisher

The repository owner is the final Publisher. The owner must explicitly decide whether the 182 entities may be approved as a single reviewed batch and whether Phase 11.10C-F may run.

### 3.3 Codex executor

Codex is not an Author, Reviewer, or Publisher. After quota reset, it may only:

- verify the expected HEAD and clean worktree;
- transfer exact files supplied by ChatGPT;
- run specified tests and temporary-database checks;
- commit only after all gates pass and the owner has authorized the commit;
- never push unless separately authorized.

## 4. Publisher state machine

```text
A. current repository
   Seed version: draft
   reviewable entities: 182 pending
   runtime DB: absent/unmodified

B. Phase 11.10C-F approved repository state
   Seed version: draft
   reviewable entities: 182 approved
   canonical hash: recomputed
   temporary SQLite publish verification: passed
   production DB: absent/unmodified
   default version: 2026.07.1

C. Phase 11.10D production runtime state
   version-controlled Seed: draft + approved
   production SQLite record: published
   runtime retrieval of 2026.08.1: available
   default version may switch to 2026.08.1 only after publication succeeds

D. remote release state
   push / PR / merge / tag / GitHub Release only under separate authorization
```

No step may be collapsed into another. A failure at any step leaves the previous valid state unchanged.

## 5. Read-only Publisher audit gates

### Gate P-01 — Repository identity

- branch is `feature/knowledge-base-v1.1`;
- HEAD is exactly `265d299ed704ec29a76470a992a94751f193ec12` before Phase 11.10C-F;
- worktree is clean;
- no merge, rebase, cherry-pick, SQLite, report, upload, or credential artifact is present.

### Gate P-02 — Software release readiness

- package and module versions are both `1.1.0`;
- complete suite: 745 tests, zero failures/errors/skips;
- branch coverage is at least 90%; measured result is 91.71%;
- Ruff and `pip check` pass;
- Python 3.12 clean-environment installation succeeds;
- Streamlit health endpoint is `ok`;
- base and enhanced paths preserve identical score and recommendation.

A Windows failure while deleting an already-validated temporary Git clone is a non-blocking cleanup warning when all core acceptance results were written first and both repositories remained clean.

### Gate P-03 — Seed identity and completeness

- knowledge version is `2026.08.1` and Seed status is `draft`;
- current canonical hash is exactly `0052ea7d63e09d8f0af49f62df8f876ac5bd2de0c8347262d67bd8e872261727`;
- counts are 3 families, 3 roles, 31 dimensions, 45 requirements, 52 patterns, 21 sources, 30 questions, 21 links, and 0 chunks;
- all 45 active requirements have at least one active same-version evidence pattern;
- all sources are used and all `license_note` fields are non-empty;
- no common hard blocker is set;
- all references are same-version and valid.

### Gate P-04 — Content and role boundaries

- AI application, data analysis, and technology strategy remain three separate role families;
- each family contains one core intern profile;
- the three unique `must_have/high` items retain tool-neutral wording;
- knowledge requirements do not enter JD scoring or score caps;
- evidence patterns remain job-knowledge guidance and never become candidate resume evidence;
- interview questions remain original prompts, not copied employer questions;
- product analysis is outside version `2026.08.1`.

### Gate P-05 — Source and rights boundaries

- 21 source records are supported by the source inventory and role review packages;
- source metadata, checksum, reliability, usage scope, and license note are present;
- no complete third-party page, job description, paid report, chart, or long quotation is stored;
- all knowledge prose and examples are original summaries;
- employer-specific tools, location, language, seniority, compensation, and management scope are not generalized;
- seven dynamic recruitment/job pages must be re-opened immediately before the approval transition;
- if any dynamic page is unavailable or materially different, Phase 11.10C-F stops and the affected source and dependent entities remain `pending`.

### Gate P-06 — Review history

The Publisher must confirm that the following completed records are sufficient evidence for batch approval:

- AI application role review and user decisions;
- data analyst role review and user decisions;
- technology strategy role review and user decisions;
- three-role consistency review and user decisions;
- release-readiness review;
- Phase 11.10B clean-environment acceptance.

### Gate P-07 — Explicit owner decision

No automated rule, previous default authorization, or Codex execution may convert review status to `approved`. The owner must explicitly approve D-01 through D-10 in the Publisher decision record.

## 6. Phase 11.10C-F transition design

After explicit approval, Phase 11.10C-F may make only the following business-content change:

```text
review_status: pending -> approved
```

It applies to exactly:

- 3 role profiles;
- 31 competency dimensions;
- 45 role requirements;
- 52 evidence patterns;
- 21 knowledge sources;
- 30 interview questions;
- 0 knowledge chunks.

No title, description, requirement type, importance, strength, question, URL, checksum, source link, alias, keyword, active flag, or hard-blocker flag may change in the same commit.

The deterministic preview hash for an otherwise unchanged Seed with all 182 review statuses set to `approved` is:

```text
346542eb0c405643a08ebc4bffdab9b5bce22a1b7227f5ad2b27f12e3d1ef7f4
```

This preview must be recomputed from the actual files after transfer. It is not a substitute for the runtime calculation.

## 7. Phase 11.10C-F required tests

### 7.1 TDD red gate

Before updating Seed statuses, tests must require:

- all 182 reviewable entities are `approved`;
- the approved canonical hash matches the expected value;
- the official Seed imports into a temporary SQLite database;
- `KnowledgeVersionPublisher.publish()` succeeds;
- the repository returns `2026.08.1` as published;
- actual official knowledge retrieval, citation validation, Report 1.1, Markdown/JSON, and Streamlit knowledge rendering succeed without changing score or recommendation.

The unchanged pending Seed must fail these new expectations.

### 7.2 Green gate

After status-only edits:

- official Seed contract passes;
- temporary import is idempotent;
- temporary publish succeeds once;
- second publish is rejected as immutable;
- persisted hash equals Seed hash;
- FTS5 and keyword fallback return deterministic results;
- complete tests and branch coverage remain at or above current release gates;
- no repository SQLite file is created.

## 8. Documentation state after Phase 11.10C-F

Documentation must describe the precise intermediate state:

```text
version-controlled Seed: draft
reviewable entities: approved
production runtime database: not imported
runtime default knowledge version: 2026.07.1
Git remote release: not performed
```

Documents must not state that the formal knowledge is available in the application until Phase 11.10D publishes the production database and switches the runtime version.

## 9. Phase 11.10D boundary

Phase 11.10D requires separate explicit authorization and must cover:

1. production runtime database path confirmation and backup policy;
2. schema initialization without touching unknown databases;
3. import of the approved `2026.08.1` Seed;
4. runtime publication and repository verification;
5. FTS5/keyword index verification;
6. default-version switch to `2026.08.1` only after publication succeeds;
7. application smoke test and rollback test;
8. final documentation, release notes, screenshot decision, history scan, push/PR/tag/Release gates.

## 10. Fail-closed conditions

Phase 11.10C-F stops without commit when any of the following occurs:

- branch, HEAD, hash, file count, or worktree differs from the approved baseline;
- a dynamic source cannot be re-opened or has materially changed scope;
- any review status is not exactly the expected transition;
- any non-review-status Seed field changes;
- approved canonical hash differs from the recomputed value;
- temporary import, publish, retrieval, citation, report, UI, tests, coverage, Ruff, or `pip check` fails;
- a repository SQLite, report, upload, credential, or private path appears;
- the production database or default version is touched;
- any tool attempts to push or create remote resources.

## 11. Design decision

The current version is technically and structurally ready for an explicit Publisher decision, but it is not publishable now because all 182 reviewable entities remain `pending` and production actions are not authorized.
