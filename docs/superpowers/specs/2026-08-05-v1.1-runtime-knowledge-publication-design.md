# JobFit Agent v1.1 Runtime Knowledge Publication Design

Authorized outcomes:

- publish approved knowledge `2026.08.1` in the formal runtime SQLite database;
- switch the effective default from `2026.07.1` to `2026.08.1`;

- screenshot changes;
- push, PR, merge, tag, GitHub Release, or moving `v1.0.0`.

## 3. Staged repository application

Repository files are applied in two stages so the source default cannot point at an unpublished target database.

### Stage 1: publication capability

Apply only:

- release safety primitives;
- publisher, rollback, and verifier scripts;
- unit and integration tests;
- this design, the implementation plan, and the runtime runbook.

The source default remains `2026.07.1` during this stage.

### Runtime transaction

Run targeted tests, then execute the publisher. The publisher changes only ignored local runtime state:

- the formal SQLite database outside Git;
- the ignored local `.env` knowledge version;
- a timestamped backup directory outside Git;
- a user-selected result JSON outside Git.

### Stage 2: completion state

Only after the publisher returns `status=passed`, apply:

- source and example default `2026.08.1`;
- config contract update;
- README, architecture, checklist, and completion record.

Then run the complete final validation and create the local commit.

## 4. Runtime path and configuration rules

The publisher loads the effective settings from the repository `.env` and resolves the database with `resolve_knowledge_db_path()`.

Safety rules:

- the runtime database must be outside the Git repository;
- `JOBFIT_KNOWLEDGE_VERSION` must not be set as a process-level override;
- process-level database-path and enabled overrides may remain only because they do not change during release or rollback;
- knowledge must be enabled;
- the effective pre-release version must be exactly `2026.07.1`;
- `.env` must be valid UTF-8 and must not contain duplicate active version assignments;
- secrets may be preserved in the private backup but never copied into the manifest, result, logs, tests, or Git.

## 5. Lock and sidecar gate

Before backup or replacement, the publisher must:

1. reject a non-file database path;
2. reject `-wal` or `-shm` sidecars;
3. obtain `BEGIN EXCLUSIVE` with zero busy timeout;
4. run `PRAGMA quick_check` and require `ok`.

The tool never stops, terminates, or kills an existing user process. A lock failure stops publication and preserves all existing state.

## 6. Backup set

A timestamped directory is created beside the runtime database under `release-backups/` unless an explicit external backup root is supplied.

The backup set contains:

- a SQLite Backup API snapshot when a live database existed;
- an exact private `.env` backup when `.env` existed;
- a secret-free publication manifest;
- candidate and effective verifier results;
- Streamlit health log;
- publication result;
- rollback script copy and PowerShell rollback command after success.

The manifest records paths, versions, Hashes, lifecycle state, and result locations, but never records `.env` content or secret values.

## 7. Shadow database publication

The candidate is created in the same directory as the live database so `os.replace()` is same-filesystem and atomic.

Candidate initialization:

- existing live database: create a consistent SQLite Backup API copy;
- missing live database: initialize compatible schema revision 1.

Target version handling:

- absent target: import approved Seed and publish;
- identical draft target: require idempotent import and publish;
- identical published target: accept as idempotent candidate state;
- mismatched, retired, or otherwise conflicting target: stop.

The candidate must expose `2026.08.1/published` with the approved Canonical Hash. FTS5 is rebuilt when available; deterministic keyword fallback remains valid when FTS5 is unavailable.

## 8. Candidate acceptance

Before cutover, the candidate must pass:

- compatible schema and published version lookup;
- AI应用实习生, 数据分析实习生, and 技术战略实习生 role isolation;
- same-version Citation existence;
- deterministic base and enhanced workflow;
- base knowledge status `disabled`;
- enhanced knowledge status `available` with at least one Citation;
- identical Job Profile, Requirement Matches, Score, and Recommendation;
- knowledge in Report, Markdown, and JSON;
- real Streamlit AppTest showing the target version, knowledge tab, Citation, and two downloads.

No external model or network service is used.

## 9. Atomic cutover and effective acceptance

After candidate acceptance:

1. prepare target `.env` content in memory;
2. recheck candidate and live SQLite access;
3. atomically replace the live database with the candidate;
4. atomically write `.env` with `JOBFIT_KNOWLEDGE_VERSION=2026.08.1`;
5. reload effective settings without temporary knowledge overrides;
6. rerun repository, three-role, Citation, Report, UI, base/enhanced identity gates;
7. start the real Streamlit application headlessly and require localhost `/_stcore/health` HTTP 200 with body `ok`;
8. terminate only the Streamlit process created by the publisher.

The source default remains `2026.07.1` until this transaction succeeds and Stage 2 is applied.

## 10. Compensation on failure

Any failure after database cutover triggers immediate compensation:

- restore the pre-release database backup, or remove the newly created database when none existed;
- write an explicit `.env` override for `2026.07.1` using the pre-release `.env` content as the base;
- verify the previous effective version and unchanged database path;
- preserve the backup directory, failure result, candidate residue if any, and compensation evidence.

A compensation failure is reported separately and never hidden.

## 11. Guarded standalone rollback

The rollback tool accepts only a completed schema `1.0` publication manifest.

Before mutation, it requires:

- current live database Hash equals the post-release manifest Hash;
- current `.env` Hash equals the post-release manifest Hash;
- exclusive database access and no sidecars;
- no process-level version override.

It snapshots the current post-release database and `.env` before restoring. It then restores the prior database state and writes an explicit `2026.07.1` `.env` assignment. If rollback fails after mutation, it attempts to compensate back to the post-release state.

The rollback never runs Git commands and never changes version-controlled Seed.
